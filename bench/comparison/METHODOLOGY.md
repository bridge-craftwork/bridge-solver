# Comparing three double-dummy solvers

How the numbers in `RESULTS.md` were taken, and why each choice was made. Not
linked from the top-level README: this is for anyone who wants to check the
comparison or repeat it, not for someone deciding whether to use the library.

The three:

| | what it is | build used |
|---|---|---|
| **DDS 2.9** | [dds-bridge/dds](https://github.com/dds-bridge/dds), the de-facto standard | `Makefiles/Makefile_Mac_clang_static` (`-O3 -flto`) |
| **C++ reference** | [macroxue/bridge-solver](https://github.com/macroxue/bridge-solver) at `75b4619` | its own `make` default: `-O3` with PGO |
| **this port** | bridge-solver | `cargo build --release` (`lto = "fat"`, `codegen-units = 1`) |

**Each is built the way its own project builds it.** That matters for the
reference in particular: its makefile's default target is
`all: solver.p solver`, where `solver` is compiled `-fprofile-use` from a
profile generated by `solver.p` on `hard_deals/deal.8`. Timing a plain `-O3`
build of it would be reporting a binary its users never run. The makefile's PGO
steps are GCC-shaped (`-fprofile-generate`, then `mv solver.p-solver.gcda`), so
on macOS they are done with the clang equivalents — `-fprofile-generate=DIR`,
`llvm-profdata merge`, `-fprofile-use=` — training on the same deal.

DDS is the reference point in every table because it is the one everybody
already has.

## Why three use cases and not one number

A single "N times faster" figure hides the thing that decides whether a solver
feels fast, because deal cost is enormously skewed. Over 2,000 random deals, by
nodes searched for the full twenty-cell table:

| | vs median |
|---|---|
| p50 | 1.00x |
| p80 | 1.92x |
| p95 | 3.59x |
| p99 | 6.11x |
| max | 10.8x |

**The slowest fifth of deals is about half of all the work, and the slowest
twentieth is a fifth of it.** So a mean over a corpus is a tail measurement
wearing a disguise, and it answers none of the three questions a user actually
has:

1. **One board, someone waiting.** A person clicks a deal and looks at the
   screen. Cores are irrelevant — one solve is one thread. What matters is the
   distribution, and specifically its top end: at the median every solver here
   is well under a tenth of a second and nobody can tell them apart, while in
   the slow tail the difference is the difference between instant and
   noticeable.
2. **One event, ~27 boards, someone waiting.** Same solves back to back. Cores
   help a little, since the boards are independent.
3. **A file of many deals.** Thousands of boards, nobody watching. Dominated by
   how well the machine's cores can be used, not by per-deal cost.

## Corpus

`gen-corpus.py` writes both input formats from one seed, so the corpus is
reproducible from the script rather than committed as data:

```bash
bench/comparison/gen-corpus.py /tmp/corpus 2000 20260902
```

Random deals, because that is what the published comparisons use and what a
user's own deals look like. `bench/corpus.json` is deliberately *not* used here
— ten curated boards are the right tool for tracking this port against itself
between commits, and the wrong one for comparing products.

`deals.pbn` is one PBN deal string per line, for `solver-bench`. `deals.hands`
is the reference's own format, four lines per deal — North, West, East, South,
suits space-separated, a void written `-`. The two are generated from the same
shuffle, and a round-trip check confirms they describe the same deals.

One wrinkle in the reference's parser is worth knowing: `ReadHands` looks for
four consecutive spaces in West's line and, finding them, takes what follows as
East. Putting every hand on its own line avoids the ambiguity entirely.

## Measuring one board (case 1)

Every solver is timed **in-process, per deal**, and the fastest of several
repeats is kept.

**Why in-process.** The reference solves one deal per invocation and has no
multi-deal input, so the obvious harness is a shell loop. That charges it
process startup *and* a cache re-grow on every deal — its `common_bounds_cache`
and `cutoff_cache` are globals that `Reset()` without shrinking, so a fresh
process starts small and grows again. Measured, that is 4.5% over 500 random
deals. On a median deal of about 90 ms it is far larger than the differences
being measured, and neither DDS nor this port pays it. So the reference is
instrumented (`ref-latency.patch`) to read a multi-deal file and time each deal
itself. The patch adds no algorithmic change and produces byte-identical tables.

**Why the minimum, and why an adaptive number of repeats.** On an 8P+4E machine
a single-threaded solve is occasionally scheduled onto an efficiency core at
roughly a third the speed. That does not average out — it adds a slow mode — so
the mean is contaminated and the minimum is not. As for how many repeats, the
two ends of this distribution want opposite treatment:

- A deal near the median is short enough that scheduling noise is a large
  fraction of it, so it wants many repeats — and being short, they are cheap.
- A deal in the slow tail is long enough that a real difference shows
  immediately, and repeating it fifteen times would dominate the run for nothing.

So the count is not fixed. Each deal is repeated until it has had a time budget
(300 ms by default), with a floor of three repeats and a ceiling of fifteen. In
practice a 30 ms deal gets ten to twelve repeats and a 900 ms deal gets three.
Both harnesses implement the identical rule.

```bash
# this port, and DDS through the same timing code
solver-bench latency /tmp/corpus/deals.pbn --runs 15 --budget-ms 300 --dds \
  --tsv /tmp/ours-dds.tsv

# the C++ reference, instrumented
LATENCY_FILE=/tmp/corpus/deals.hands LAT_RUNS=15 LAT_BUDGET_MS=300 \
  ./solver-ref-latency > /tmp/ref.tsv
```

DDS is measured through `CalcAllTablesPBN` one deal at a time. Batching it
forty deals to a call was checked and is worth nothing at one thread — 53.3 s
against 52.9 s over 500 deals — so the per-deal call is not handicapping it.
DDS's threading backend is set to STL rather than its macOS default of GCD,
which dispatches at background priority and so lands on the efficiency cores.

**A board is the full twenty-cell table** — five strains by four declarers.
That is what all three produce by default and what a UI showing a deal's
double-dummy table needs.

## Measuring an event and a file (cases 2 and 3)

Wall clock for the whole set, which is what a user waits on.

**The reference cannot use threads.** It has none — no `std::thread`, no
`fork`, no `posix_spawn` anywhere in `solver.cc` — and it could not use them if
it wanted to, because `common_bounds_cache`, `cutoff_cache` and `stats[]` are
global mutable state written during the search. Its README says so plainly:
"The solver is single-threaded, so multiple instances of the solver are running
in parallel." Its own `parallel_run_tests.sh` fans out with
`xargs -L 1 -P N`, one process per deal, and there is no interface for a file
of deals — `main` accepts `-c` (one deal), `-f` (one deal) or `-r` (one random
deal), and orchestration is left to the user.

That is a packaging difference as much as a performance one, and the comparison
reports it as such. For case 3 the reference is therefore driven the way it is
meant to be driven, `xargs -P N` over one file per deal, and the metric is
deals per second achieved on the machine. That is a fair comparison of
outcomes: DDS and this port use threads, the reference uses processes, and the
user gets whatever the machine delivers. The per-deal process cost is genuinely
part of the reference's cost in this mode, so unlike case 1 it is not
instrumented away.

## What is not controlled

- **One machine.** Everything here is an Apple M4 Pro. The reference has an
  x86-only fast path — `PackBits`/`UnpackBits` are `_pext_u64`/`_pdep_u64`
  under `__BMI2__`, and its makefile adds `-mbmi2` when `/proc/cpuinfo` says so
  — that aarch64 cannot have. Measured, that is worth roughly 5% to it; see
  `../results/release-profile.md`. DDS has no architecture-specific code at
  all, so it neither gains nor loses. Numbers from an x86-64 machine will not
  match these, and the direction of the difference is known.
- **DDS version.** 2.9 only.
- **Machine load.** These runs were not taken on an idle machine. The
  minimum-of-repeats rule is what makes that tolerable for case 1; cases 2 and
  3 are whole-machine measurements and are more exposed, so they are taken
  interleaved and repeated.
